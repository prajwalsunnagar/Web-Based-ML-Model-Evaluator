A comprehensive verification of the Sprint 1 implementation against the approved SRS, SAD, and Test Plan was conducted. The core ML evaluation workflow is fully functional, robustly tested, and compliant with all mandatory functional and non-functional requirements allocated to Sprint 1.

## 3. Verified Deviations from Submitted Documents

### Deviation 1: Local Streamlit Engine vs. Proposed REST API Service
- **Submitted Baseline (SAD Section 4.5):** Proposed HTTP REST endpoints (`POST /api/datasets`, `POST /api/evaluations`, `GET /api/evaluations/{id}`).
- **Actual Implementation:** Integrated modular service package (`evaluator.engine`, `evaluator.metrics`, `evaluator.validators`) directly invoked by the Streamlit application and pytest suite.
- **Reason & Engineering Justification:** Eliminates unnecessary network overhead and port serialization for a desktop/web evaluation utility. The domain logic remains decoupled in the `evaluator/` module and can be exposed via FastAPI/Flask in the future without modifying core calculation code.
- **Impact:** Zero impact on end-user evaluation functionality; significantly faster execution and simpler local/CI testing.

### Deviation 2: Prediction File Evaluation vs. Serialized Model Weight Execution
- **Submitted Baseline (SRS Section 1.2):** Left open whether the system evaluates uploaded predictions or executes serialized binary model weights (`.pkl`, `.onnx`).
- **Actual Implementation:** Accepts paired CSV datasets containing reference ground-truth values and model predictions.
- **Reason & Engineering Justification:** Uploading serialized model files introduces severe remote code execution (RCE) security risks (e.g., Python `pickle` exploits, `SEC-07`). Evaluating predictions decouples the tool from arbitrary ML training libraries (PyTorch, TensorFlow, XGBoost) and ensures universal cross-platform compatibility.
- **Impact:** Positive security posture; broader applicability to predictions generated by any model runtime.

### Deviation 3: Single-Tenant Browser Session vs. Multi-User Authentication (`FR-12`, `TC-10`)
- **Submitted Baseline (SRS Section 4.1 & Test Plan TC-10):** Conditionally noted: *"If user accounts are implemented, the system shall prevent a user from viewing another user's restricted run."*
- **Actual Implementation:** Single-tenant session state. No authentication layer or central database is implemented.
- **Reason & Engineering Justification:** The project scope was defined as a lightweight web-based evaluation tool. Adding database auth would introduce out-of-scope operational complexity for Sprint 1.
- **Impact:** `TC-10` is formally marked `N/A (Documented)`. All runs within an active browser session are strictly isolated to that client.
